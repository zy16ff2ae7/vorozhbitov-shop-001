# Обновление и восстановление

Изменения схемы аддитивные: при запуске создаются `checkouts`, `payment_methods`, `notifications`, `provider_transactions`, `refund_events` и поля возврата/подарочного резерва. Старые пользователи, заказы и платежи не переписываются автоматически. Версия знает `refund_required`, односторонний переход `refund_required → refunded` и полную `refund_amount_rub`.

## Перед обновлением

1. Зафиксируй версию образа/коммит и текущую конфигурацию. Закрой создание новых заказов на время обслуживания.
2. Останови приложение: `docker compose stop bot`. Дождись остановки перед копированием SQLite. Сохрани **всю папку `data/`**, включая возможные `bot.sqlite3-wal` и `bot.sqlite3-shm`, каталог и отдельную копию конфигурации. Храни резервную копию вне web-root с ограниченными правами.
3. На копии базы выполни `PRAGMA integrity_check;`. Не запускай вторую копию polling с боевым токеном.
4. Сверь старые аномальные заказы запросами ниже. Не выставляй новые счета автоматически: старые ссылки у провайдеров могут оставаться действительными.
5. Собери/запусти новую версию. Проверь `/health`, каталог и проход тестового заказа до создания счёта. Полноценную проверку списания/возврата проводи только на тестовых настройках провайдеров.

## Автоматический backup и restore drill

Фоновый maintenance loop раз в UTC-сутки создаёт `data/backups/bot-YYYY-MM-DD.sqlite3` через SQLite online backup API. Снапшот согласован с WAL, записывается во временный файл, синхронизируется через `fsync`, получает права `0600` и атомарно переименовывается. Хранятся семь последних файлов; после временной ошибки watermark не продвигается, поэтому следующая попытка выполняется через несколько секунд.

Это локальная страховка, не внешний backup: при потере всего диска `data/backups/` исчезнет вместе с базой. Настрой регулярное копирование каталога в отдельное зашифрованное хранилище и контроль свободного места.

Проверка восстановления (на отдельной копии, без боевого polling):

```bash
# Выбери существующий снапшот, не подставляя имя вслепую.
ls -l data/backups/bot-*.sqlite3
python3 - <<'PY'
import sqlite3
source = sqlite3.connect('file:data/backups/bot-2026-10-24.sqlite3?mode=ro', uri=True)
target = sqlite3.connect('/tmp/vorozhbitov-restore-drill.sqlite3')
source.backup(target)
print(target.execute('PRAGMA integrity_check').fetchone()[0])
target.close(); source.close()
PY
```

Для боевого восстановления останови приложение, сохрани текущую базу отдельно, восстанови выбранный снапшот через backup API или файловую копию, удали устаревшие `-wal/-shm` только после остановки, проверь `integrity_check` и права UID 10001. Не запускай одновременно старый и новый polling с одним токеном.

## Каталог: что можно и чего нельзя

`catalog.json` правится из чата (`/add`, `/hide`, `/show`) — это предпочтительный
путь: бот проверяет значения до записи и не может записать файл, который сам не
примет.

При ручной правке файла помни:

- **Старт с битым файлом невозможен.** Бот завершится с кодом 2 и строкой
  `catalog.json не прошёл проверку (...): <причина>`. Это защита, а не сбой:
  витрина с непроверенным каталогом ломала бы кнопки покупок.
- **`/reload` битый файл не применяет.** Ответит «КАТАЛОГ НЕ ПЕРЕЧИТАН», назовёт
  причину и продолжит работать с последним хорошим каталогом в памяти.
- id вещи — до 40 байт, id раздела — до 48, `size:<id>:<размер>` — до 64 байт
  целиком, двоеточия внутри id и размеров запрещены, дубли id запрещены.
- вещь обязана ссылаться на существующий раздел: удаление раздела, на который
  есть вещи, сделает файл непроходимым.
- цена должна быть одним числом в целых рублях; ненулевые копейки и диапазоны не проходят checkout. Ошибочное поле каталог не роняет при чтении, но счёт по такой вещи не выставляется — в логе будет ERROR.

После ручной правки проверь файл запуском тестов и только потом делай `/reload`.

## Сверка данных

Запросы выполняются на копии базы и ничего не меняют:

```sql
-- Заказы с отсутствующим платежом.
SELECT o.id, o.payment_id, o.status
FROM orders o LEFT JOIN payments p ON p.payment_id=o.payment_id
WHERE o.payment_id<>'' AND p.payment_id IS NULL;

-- Сумма платежа отличается от стоимости связанных позиций.
SELECT p.payment_id, p.amount_rub, COALESCE(SUM(o.amount_rub),0) AS order_total
FROM payments p LEFT JOIN orders o ON o.payment_id=p.payment_id
GROUP BY p.payment_id
HAVING p.amount_rub <> COALESCE(SUM(o.amount_rub),0);

-- Требующие ручной сверки поступления.
SELECT payment_id, amount_rub, refund_amount_rub, method, provider_id, status
FROM payments WHERE status='refund_required';

-- Отдельные транзакции провайдера, включая зафиксированные переплаты.
SELECT provider, provider_transaction_id, payment_id, amount_rub, currency, status
FROM provider_transactions ORDER BY created_at DESC;

-- Задания уведомлений, ожидающие доставки.
SELECT notification_id, attempts, next_attempt_at
FROM notifications WHERE delivered_at IS NULL;
```

`refund_required` означает, что деньги поступили по отменённой/несогласованной заявке либо администратор отменил оплаченную корзину. Одна оплата является единой единицей исполнения: отмена любой её позиции отменяет все связанные позиции и сохраняет полную `refund_amount_rub`; частичный возврат через обычную кнопку не маскируется под полный. Сверь поступление и сумму у провайдера, выполни возврат вручную и сохрани подтверждение в журнале менеджера. Кнопка «выполнен» меняет только разрешённый переход `refund_required → refunded` и не является API-подтверждением провайдера. Статус нельзя вручную возвращать в `pending`: это повторно откроет оплату.

## Откат

Если после обновления новые заказы и платежи ещё не принимались, останови приложение, восстанови **парой** предыдущий образ/коммит и резервную копию `data/`, проверь права UID 10001 и запусти прежнюю версию.

Если после обновления уже поступали заказы или деньги, не восстанавливай старую базу поверх новой: так потеряются операции. Сохрани копию текущей базы и выполни исправление вперёд или ручную сверку. Старый код не понимает `refund_required` и новые ключи checkout, поэтому откат только кода с продолжением продаж на новой базе небезопасен.

## Retention служебных данных

Maintenance-loop не чаще одного раза в сутки удаляет доставленные notification-envelope старше 30 дней, истёкшие больше суток `payment_methods` и высокочастотные browsing/session events старше 90 дней. Недоставленные уведомления не удаляются: их нужно чинить и мониторить. Платежи, счета, транзакции провайдеров, заказы, возвраты, согласия, admin/referral и финансовые события этой очисткой не затрагиваются. Backup делается до очистки; внешняя копия нужна для восстановления старше retention-окна.

## Сеть и наблюдение

Backend опубликован на loopback; снаружи доступен только TLS reverse proxy. Прокси должен обслуживать весь `/api/`, включая webhook, перезаписывать `X-Real-IP` и ограничивать размер/время HTTP-запросов. Укажи точный адрес прокси в `TRUSTED_PROXY_IPS`, иначе лимитер будет учитывать его посетителей как один IP.

`/health` — readiness: HTTP-процесс выполняет SQLite `quick_check` и читает актуальный каталог, при недоступной зависимости отвечает 503. Она не заменяет отдельный liveness и наблюдение за ошибками polling Telegram, очередью `notifications`, статусами `refund_required`, переплатами в `provider_transactions`, сроком последнего backup и свободным местом на диске. Логи не публикуй через web-root.
