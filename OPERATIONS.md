# Обновление, сверка платежей и восстановление

## Что меняется в версии после аудита 10 сентября

Миграция схемы аддитивная. Помимо `checkouts`, `payment_methods` и `notifications`, создаются:

| Таблица | Назначение |
|---|---|
| `payment_inbox` | Минимальные финансовые Telegram updates, lease, попытки и результат обработки |
| `payment_invoices` | Выданные внешние счета: provider ID, внутренний payment ID, внешний reference, ожидаемые сумма/валюта, URL |
| `payment_invoice_attempts` | Попытки создания счетов, включая неопределённый результат и старые непроверенные ссылки |
| `payment_receipts` | Каждое отдельное поступление; уникальность `(method, provider_id)` |
| `payment_receipt_conflicts` | Один charge ID с противоречащими полями/привязками |

Старые пользователи, заказы, суммы и статусы платежей не переписываются автоматически. Исключение для приватности: из временных состояний `awaiting_consent` удаляется старое поле `next_data.phone`; его нельзя использовать как номер, полученный после согласия. Это логическая очистка таблицы, не удаление старых резервных копий/WAL на носителях.

Непустые исторические charge ID импортируются идемпотентно с `source=legacy`, `status=legacy_unreconciled`. Это **копия старого локального состояния, не подтверждение от провайдера**. Новые уведомления об оплате и повторная отгрузка при миграции не создаются. Добавленный позже финансовый worker может завести рабочие задачи и служебные напоминания по историческим исключениям — это не новые деньги. Противоречащие старые привязки сохраняются отдельно. Исторический код мог обрезать ID до 80 символов; восстановить исходный ID из обрезанного нельзя.

## Перед обновлением

1. Зафиксируй версию образа/коммит и текущую конфигурацию. Закрой создание новых заказов на время обслуживания. Действующие ссылки у провайдеров от этого не перестают принимать деньги.
2. Останови приложение: `docker compose stop bot`. Сохрани **всю папку `data/`**, включая возможные `bot.sqlite3-wal`, `bot.sqlite3-shm` и каталог. Конфигурацию сохрани отдельно, вне web-root, с ограниченными правами.
3. На копии базы выполни `PRAGMA integrity_check;` и `PRAGMA foreign_key_check;`. Прогони миграцию и локальные регрессии. Не запускай вторую копию polling с боевым токеном.
4. Сверь открытые старые счета с кабинетом/API соответствующего проекта провайдера. **Не перевыставляй их автоматически** и не восстанавливай invoice ID из входящего webhook, URL или предположения, что он равен payment ID. Также проверь возможные дубли заявок, созданные старым клиентом: миграция их не удаляет.
5. Проверь отдельный `LAVA_HOOK_KEY`: теперь без него Lava отключена. Это дополнительный ключ уведомлений, не fallback на исходящий `LAVA_SECRET_KEY`. Никакие значения `.env` миграция не меняет.
6. Убедись, что настроен `MANAGER_CHAT_ID`, контролируются очереди и есть ответственный за сверку/возвраты. Уведомления об аномалиях при отсутствии manager ID направляются настроенным администраторам; финансовый пульт также использует актуального ответственного/роль `finance` и сохраняет неадресованное намерение в `finance_alerts`. Подробный маршрут описан ниже.
7. Собери/запусти новую версию. Проверь `/health`, каталог, все три фоновых направления: polling, payment inbox, notification outbox. Пройди отдельный тестовый заказ на **тестовых** настройках Telegram/провайдеров, включая настоящий формат webhook и возврат. Локальные моки не заменяют эту проверку.

## Старые и неопределённые счета

- Старые cached URL без сохранённого invoice ID получают `legacy_unverified`. Эта ссылка не выдаётся повторно, новый счёт тем же методом автоматически не создаётся.
- До обращения к провайдеру сохраняется попытка `creating`. После успешного сохранения invoice ID она становится `issued`. Ошибка/таймаут получает `uncertain`; при аварийном завершении может остаться `creating`. В обоих случаях повторное создание блокируется: провайдер мог уже создать счёт.
- После независимой сверки оператор может привязать подтверждённый старый счёт через `Database.save_invoice(...)`: нужны точные ID, `external_ref`, сумма в копейках, RUB, URL и соответствующий `attempt_id`. Этот внутренний метод не делает сетевых запросов и сам **не является проверкой у провайдера**. Не вызывай его по данным одного непроверенного уведомления.
- Снимать блокировку неудачной попытки допустимо только после подтверждения отсутствия/окончательной недействительности счёта у провайдера. При неоднозначности оставь блокировку и направь клиента на сверку, а не новую оплату.
- Crypto-счёт переиспользуется и после 30-минутного истечения кэша кнопок, пока действует его часовой срок. После срока новый ID допустим только пока сама покупка и её складской резерв ещё действуют; истечение резерва не разрешает перевыпуск. Старый ID остаётся в журнале, позднее поступление не теряется.
- У Lava неизвестный срок не угадывается: сохранённая ссылка переиспользуется без автоматического перевыставления по таймеру. Если она истекла, сначала проверь статус/срок у провайдера; не закрывай её только по возрасту локального кэша. Новый `orderId` формируется уникальным для каждой подтверждённо новой попытки.

Счета, выданные старой версией, но уже отсутствующие даже в локальном кэше, восстановить автоматически невозможно. Их необходимо учитывать при сверке кабинета провайдера.

## Как понимать статусы

- `payment_receipts.applied`: поступление применено к заявке один раз; цена/валюта/привязка совпали, для Stars повторно проверен владелец.
- Дополнительный distinct charge после подтверждённой оплаты: `payment_receipts.refund_required`, причина `extra_payment`. **Исходные `payments.method/provider_id` и оплаченный заказ не затираются.** Поэтому поиск только `payments.status='refund_required'` недостаточен!
- Поступление после ручной отметки или непроверенного исторического расчёта: отдельный `review_required`. Нельзя предположить, что ручная отметка и webhook означают два разных перевода.
- Подписанные уведомления с неизвестным счётом, неверной суммой/валютой/привязкой — `review_required`, не оплаченный заказ. Для связанного ожидающего платежа новая оплата блокируется. «Мои заявки» показывает сверку без кнопок оплаты/отмены.
- Поздняя оплата отменённой заявки либо отмена оплаченной позиции администратором требует возврата/сверки, не возобновляет исполнение.
- `payment_receipt_conflicts` требует проверки, даже если первоначальная запись уже была оплачена.

Сверь реальное поступление, владельца, комиссии и сумму возврата у провайдера. Если уполномоченный сотрудник затем исполняет возврат в кабинете провайдера, подтверждение нужно хранить в согласованной финансовой системе. Приватная заметка по задаче в `/finance` фиксирует ход разбора, но не интегрируется как доказательство исполнения и не меняет деньги. **Автоматические возвраты, подтверждение их исполнения и интерфейс снятия блокировки сверки не входят в эту версию.** Не меняй `review_required`/`refund_required` обратно на `pending` ради исчезновения предупреждения: это снова откроет оплату. Разблокировка/исправление спорной привязки требует отдельной контролируемой операции после сверки, не повторного webhook и не повтора заказа.

## Подписи и суммы

Lava подписывается HMAC-SHA256 от тех же UTF-8 JSON bytes, которые отправляются по HTTP. Входящая подпись проверяется по raw body отдельным ключом. Реализация работает с RUB-счетами: отсутствие поля currency допустимо **только** при уже сохранённом RUB invoice; явно другая валюта отправляется на сверку. Перед релизом проверь этот контракт на актуальном тестовом webhook Lava Business API ([документация](https://developer.lava.ru/)).

Crypto требует `update_type=invoice_paid`, внутренний `status=paid`, `currency_type=fiat`, RUB и сохранённый invoice ID. Суммы провайдера преобразуются через Decimal в целые копейки; NaN, бесконечность и лишняя точность отклоняются. Stars — только целые XTR, без округления дробных значений.

Подтверждённые подписью, структурно корректные, но несогласованные поступления сохраняются на сверку и получают HTTP 200. Невалидные подпись/JSON/обязательные поля отклоняются. При ошибке записи оплаты возвращается HTTP 503, а не успех. Успех окна Telegram или redirect провайдера не заменяет серверное подтверждение заказа.

## Контрольные запросы

Запросы ниже только читают. Не публикуй их результаты: они содержат финансовые и пользовательские идентификаторы.

```sql
PRAGMA integrity_check;
PRAGMA foreign_key_check;

-- Зависшие финансовые updates: уже приняты локально, но ещё не обработаны.
SELECT update_id, attempts, next_attempt_at, received_at, last_error
FROM payment_inbox WHERE processed_at IS NULL;

-- Аномалии каждого поступления, включая переплату по уже оплаченному заказу.
-- amount_minor: копейки для RUB, целые звёзды для XTR. Не суммируй разные валюты.
SELECT receipt_id, payment_id, method, provider_id, amount_minor, currency,
       status, reason, received_at
FROM payment_receipts WHERE status IN ('review_required', 'refund_required');

SELECT * FROM payment_receipt_conflicts;

-- Наследованные состояния отдельно от новых денежных событий.
SELECT receipt_id, payment_id, method, provider_id, status
FROM payment_receipts WHERE source='legacy';

-- Неопределённые попытки и неподтверждённые старые ссылки.
SELECT attempt_id, payment_id, method, external_ref, status, created_at
FROM payment_invoice_attempts WHERE status IN ('creating','uncertain','legacy_unverified');

-- Заказы без платежа или с рассогласованной суммой.
SELECT o.id, o.payment_id, o.status
FROM orders o LEFT JOIN payments p ON p.payment_id=o.payment_id
WHERE o.payment_id<>'' AND p.payment_id IS NULL;

SELECT p.payment_id, p.amount_rub, COALESCE(SUM(o.amount_rub),0) AS order_total
FROM payments p LEFT JOIN orders o ON o.payment_id=p.payment_id
GROUP BY p.payment_id HAVING p.amount_rub<>COALESCE(SUM(o.amount_rub),0);

SELECT payment_id, amount_rub, method, provider_id, status
FROM payments WHERE status IN ('review_required','refund_required');

SELECT notification_id, attempts, next_attempt_at
FROM notifications WHERE delivered_at IS NULL;
```

## Гарантии и границы очередей

`successful_payment` из Telegram сохраняется **до продвижения polling offset**. Ошибка enqueue оставляет offset прежним. Inbox содержит только update/user/chat ID и минимальные финансовые поля, без всего message, профиля, contact или `order_info.phone_number`. Worker повторяет обработку независимо от сетевой доставки сообщений. Receipt, статусы, события, outbox и отметка обработки inbox фиксируются одной транзакцией. WAL работает с `synchronous=FULL`.

Обычные сообщения и callback updates не получили универсальный inbox: их обработка по-прежнему best effort. Не называй это exactly-once для всего Telegram. Доставка исходящих сообщений — как минимум один раз: авария между отправкой и записью результата может повторить уведомление, но не заказ/поступление. Очереди, свободное место и реальные ошибки fsync требуют мониторинга; `/health` проверяет только доступность HTTP-процесса.

## Локальные данные витрины

Профиль, корзина, избранное, история и pending checkout разнесены по Telegram user ID; предпросмотр имеет отдельную область. Это UI-изоляция аккаунтов, **не шифрование** данных общего браузера и не серверная авторизация. Сервер продолжает проверять подпись initData и владельца.

Старые общие профиль/корзина/история не переносятся автоматически: после обновления данные может понадобиться заполнить заново. Переносится только прежний pending request, уже адресованный тому же user ID. Кнопка удаления очищает текущую область и старые общие ключи; сохранённые заявки на сервере и области других Telegram-аккаунтов не удаляются. При запрете записи localStorage retry сохраняется в памяти страницы; гарантировать сохранение после её закрытия нельзя.

## Откат и сеть

Если новые заказы/поступления ещё не принимались, останови приложение и восстанови **парой** предыдущий образ/коммит и резервную копию `data/`, проверь права UID 10001. Если новые операции уже были, не накатывай старую базу поверх новой: сохрани актуальную копию и исправляй вперёд после сверки. Старый код не учитывает новые receipt/inbox/блокировки; откат только кода с продолжением продаж небезопасен.

В боевом окружении снаружи доступен только TLS reverse proxy. Он должен обслуживать весь `/api/`, включая webhook, перезаписывать `X-Real-IP` и ограничивать размер/время запросов. Укажи точный адрес прокси в `TRUSTED_PROXY_IPS`. Логи, БД и резервные копии не публикуй через web-root.

## Торговое ядро: 11 сентября 2026

### Аддитивная миграция

Добавлены `shopping_carts`, `cart_lines`, `cart_mutations`, `purchases`, `stock_items`, `stock_reservations`, `stock_movements`, `staff_roles`, `staff_audit`, `chat_actions`, `chat_action_results`, `chat_panels`, `checkout_drafts`.

В `users` добавлены `customer_name` и `service_only`, в `orders` — `person`. Не восстанавливаем имя получателя из регулярно обновлявшегося Telegram first name. Новое согласие на обслуживание покупки не включает массовые рассылки; прежний тип согласия не переопределяется автоматически.

Старые оплаты с согласованными по владельцу строками группируются в `purchases` с `stock_managed=0`. Миграция не создаёт резервы, не списывает товар, не меняет финансовые суммы/статусы и не повторяет уведомления. Строки без оплаты и с противоречащими владельцами не превращаются в новые покупки; остаются для сверки в прежнем архиве. Смешанная по владельцам оплата не считается доступной к оплате. Legacy-флаг — предупреждение о необходимости ручной сверки, не доказательство выделения товара.

### Пересчёт перед продажами

1. Выполни основной план резервного копирования и сверки выше. Обновление кода само по себе **не включает безопасную продажу неизвестных остатков**.
2. Сверь все оплаченные, ещё действующие исторические счета и уже выделенные под старые обязательства вещи. Если старый счёт остаётся действующим, его обязательство нельзя игнорировать только потому, что в новой таблице нет резерва. При нехватке сначала согласуй решение и сверку, не продавай эти единицы вторично.
3. Владелец из `ADMIN_IDS` открывает `/stock`. Для каждого SKU подтвердить товар, размер и product ID. Ввести число, затем подтвердить пересчёт.
4. **Вводимое `on_hand` — ещё не списанный товар для продажи**, включая текущие неоплаченные резервы. Уже оплаченные и выделенные старым обязательствам единицы исключить. `available = on_hand - reserved`. Это не общий физический остаток всех зон склада.
5. Неизвестно (`NULL`) отличается от подтверждённого нуля. Не использовать `stock_label`, `active`, видимость размера, количество фото или `commerce_test_support.py` для «заполнения склада». Тестовый helper импортируется только тестами/демо и не входит в Docker-образ.
6. Если с момента открытия карточки изменился резерв или версия SKU, пересчёт отклоняется. Обновить карточку и пересчитать, а не подменять версию. Ниже активного резерва число не принимается: сначала решить связанные неоплаченные обязательства с ответственным.
7. После пересчёта проверить отдельную тестовую покупку, отмену, оплату, рестарт и истечение резерва. Дополнительно подтвердить правила доставки, юридические тексты, права на материалы и допустимость выбранных платёжных методов для товаров/территории. Локальные тесты этого не подтверждают.

Новые SKU после `/add` и новые размеры после обновления каталога остаются неизвестными до пересчёта. Скрытие товара не удаляет историю и не возвращает списанный товар. `/restock ID SIZE` больше не рассылает сообщения. Подтверждённый пересчёт выполняется через `/stock`, а уведомления работают только по отдельному согласию `/alerts`; диагностика — `/alertdesk`.

### Работа команды

- Сотрудник открывает бота; владелец назначает роль через `/role ID manager|warehouse|support` с подтверждением. Отзыв — `/role ID none`.
- `/team` или `/admin` — рабочий пульт. Менеджер видит целую покупку, берёт её и подтверждает реальные этапы. Поддержка не изменяет покупки; склад не получает контактный снимок.
- `MANAGER_CHAT_ID` получает короткое уведомление и ссылку на карточку, но само наличие в этом чате не даёт прав. Рабочие карточки открываются только в личке с проверкой роли.
- При уходе/отзыве сотрудника владелец снимает назначение и возвращает покупку в очередь. Платёж и фактический этап этим не меняются.
- Новые роли, складские пересчёты, назначения и этапы попадают в `staff_audit`. Это не обещание полного аудита всех прежних команд владельца: старые рассылки/каталог/экспорт по-прежнему имеют свои прежние механизмы.
- Не завершать финансовую сверку одной сменой статуса заказа. Ручные этапы не являются трекингом перевозчика или доказательством оплаты.

### Резерв и поздняя оплата

Резерв создаётся в той же `BEGIN IMMEDIATE`, что покупка, оплата, позиции, очистка нужной версии корзины и outbox. Ошибка любой части откатывает всё это. Новый резерв — 3600 секунд. Worker финансового inbox также освобождает истёкшие резервы; проверки при открытии покупок дают дополнительную актуализацию.

`held → consumed` уменьшает `on_hand` и `reserved`; `held → released` уменьшает только `reserved`. Повтор поступления/команды не повторяет движение. При истечении обычная неоплаченная покупка становится `expired`, позиции отменяются. При финансовом `review_required` резерв освобождается, но **сам review и receipt сохраняются**.

Внешняя ссылка может оставаться способной принять деньги после локальной отмены/истечения. Успешное позднее поступление не возобновляет исполнение и не расходует новую бронь другого клиента: нужна сверка/возврат. Возврат денег не вызывает автоматический приход товара. После фактического возврата и проверки вещи разрешён отдельный подтверждённый пересчёт склада.

### Контрольные запросы склада

Только чтение; результаты не публиковать.

```sql
-- Неизвестные варианты: продажи для них ещё не подготовлены.
SELECT sku_id, product_id, size FROM stock_items WHERE on_hand IS NULL;

-- Любая строка здесь требует остановить спорные действия и проверить учёт.
SELECT s.sku_id, s.product_id, s.size, s.on_hand, s.reserved,
       COALESCE(SUM(CASE WHEN r.state='held' THEN r.quantity ELSE 0 END),0) AS held_sum
FROM stock_items s LEFT JOIN stock_reservations r ON r.sku_id=s.sku_id
GROUP BY s.sku_id
HAVING s.reserved<>held_sum OR s.on_hand<s.reserved;

-- Просроченные, ещё не освобождённые резервы: проверить worker/ошибки БД.
SELECT r.payment_id, r.sku_id, r.quantity, r.expires_at, p.status
FROM stock_reservations r JOIN payments p ON p.payment_id=r.payment_id
WHERE r.state='held' AND r.expires_at<CAST(strftime('%s','now') AS INTEGER);

-- Исторические обязательства без автоматически восстановленного резерва.
SELECT u.purchase_id, u.payment_id, p.status
FROM purchases u JOIN payments p ON p.payment_id=u.payment_id
WHERE u.stock_managed=0;

SELECT actor_id, action, entity, before_data, after_data, created_at
FROM staff_audit ORDER BY audit_id DESC LIMIT 50;
```

Не исправлять расхождение арифметики прямым `UPDATE reserved=0`: можно повторно продать уже обещанный товар. `stock_movements` — журнал операций; `count` содержит подтверждённое целевое количество, а не универсальную дельту, поэтому нельзя просто суммировать его `quantity` вместе с остальными типами.

### Cart API и восстановление

Все account/cart/purchases API требуют подписанную initData. Пользователь из body/query не используется как источник полномочий. На POST корзины нужны `items`, текущая `revision` и стабильный `operation_id`; повтор операции с другим телом запрещён. HTTP 409 не разрешает автоматически брать новую версию и перезаписывать её: выбор должен быть явным.

`cart_revision` принятого checkout хранится в неизменяемом retry-запросе. При таймауте, 503 и неопределённом ответе не менять request ID, состав, профиль или версию ради «повторить». Исключение — явно возвращённый `cart_revision_conflict`: проверка внутри транзакции доказала, что эта версия уже устарела; идентичное тело с ней не сможет создать новую покупку. После обновления/явного выбора корзины разрешён новый запрос. Для legacy-запросов без версии это исключение не применяется.

После успешного checkout клиент не очищает новую локальную правку другого окна и не отправляет слепой POST пустой корзины. Если новый состав ещё не сохранён на сервере, он остаётся локально с запросом разрешить конфликт.

Локальная очистка выставляет несекретный `#local-only`: автовосстановление профиля и корзины выключается в этом окне, ручные кнопки остаются. Это не удаление серверных персональных данных или финансовых документов. Новый запуск из бота может снова загрузить серверный профиль; для его удаления/ограничения требуется отдельный операционный процесс.

Временные actions очищаются после срока плюс сутки, mutations и checkout previews — через 7 дней. История денег, покупок, движений и staff audit этой очисткой не удаляется. Политику хранения/удаления персональных данных, копий и носителей необходимо утвердить отдельно.

**Не разворачивать `tools/bot_demo.py` или `tools/ui_test_server.py` как рабочий сервис.** В первом роли переключаются без авторизации, у второго намеренно публичный тестовый токен и ослабление frame-ограничения только для офлайн-превью. Рабочий `bot.py` этих исключений не получает.

## Доставка и поддержка: этап 2

Описание пользовательских сценариев и точные границы — в [BOT-OPERATIONS-IMPLEMENTED.md](BOT-OPERATIONS-IMPLEMENTED.md).

### Перед обновлением и первая передача

1. Сделать проверенную резервную копию SQLite вместе с согласованным состоянием WAL, сохранить предыдущий код. Не копировать работающий SQLite-файл отдельно от журнала; использовать backup API/плановую остановку. Резервная копия содержит персональные данные.
2. При запуске аддитивно создаются таблицы операций и `purchases.operations_managed`. Старые покупки имеют `0` без фиктивного тарифа, трека или даты вручения. Не включать `1` массовым SQL. Новые checkout получают `1` и пустой план в транзакции покупки.
3. Утвердить юридические тексты, правила обмена/возврата, доступ сотрудников и сроки хранения переписки/адресов. Разрешение на обслуживание не заменяет согласие на рекламу.
4. Проверить у реального перевозчика доступность адреса/ПВЗ, стоимость и срок. Бот сам ничего из этого не рассчитывает. Ввод цены — в рублях до двух знаков, хранение — в копейках. Не выдавать оценку за подтверждённый тариф.
5. Менеджер из покупки предлагает условия: способ → кто рассчитывается → адрес → сумма при расчёте с перевозчиком → оценка срока → источник → проверка → отправка покупателю. Покупатель отдельно принимает их.
6. Для передачи нужны оплаченные товары без сверки, сборка `ready`, действующее согласие и отсутствие блокирующих обращений. Ответственный фиксирует только состоявшуюся передачу или реальную готовность самовывоза. Новый счёт за доставку не создаётся.
7. Фактическое вручение подтверждает покупатель либо назначенный сотрудник/владелец. Проверить источник в карточке. Это ручной учёт, не API/OTP-доказательство. Новые покупки нельзя завершить обходной командой статуса до вручения.

Самовывоз в этой очереди без доплаты. При доставке возможен только прямой расчёт покупателя с перевозчиком либо покрытие стоимости магазином с доплатой `0`. **Не менять `payments.amount_rub` ради доставки, не применять дополнительное поступление как доплату и не очищать `payment_attention` закрытием обращения.**

После передачи адрес и стоимость прежних условий не редактируются. Исправление трека до вручения — менеджером/владельцем, с причиной, историей и уведомлением. При проблеме отправления сотрудник создаёт связанное обращение через карточку; автоматически «возвращено»/«деньги возвращены» не проставляется.

### Очереди и ответственность

- `/shipping` — согласование, к передаче, в пути/выдача, вручено. Карточки с блокировкой могут присутствовать в очереди подготовки; наличие в списке не является разрешением передавать.
- `/desk` — открытые/мои/закрытые обращения. Сначала взять в работу, затем ответить. Внутренняя заметка отделена от публичного ответа и не вызывает уведомления покупателю.
- Связанные вопросы доставки/адреса, обмена, возврата и оплаты требуют решения менеджера/владельца либо явного отзыва покупателем. До передачи они блокируют её; после передачи/вручения не меняют совершённый факт. Обычный ответ поддержки финансовый review не снимает.
- `blocks_dispatch` в таблице обращения хранит признак чувствительного связанного кейса. Реальная пауза есть только у незакрытого кейса до передачи активной покупки. DTO `blocks_dispatch` учитывает физический этап; `requires_manager` отдельно указывает чувствительное решение.
- Закрытие требует публичного итогового текста. Покупатель может возобновить закрытое обращение. Это не интерфейс исполнения возврата, не складской приход и не отмена внешнего счёта.
- Вернуть своё назначение в общую очередь может ответственный, чужое — владелец. После отзыва роли поддержки/менеджера назначения **обращений** автоматически освобождаются; назначение **покупки** владелец по-прежнему снимает через рабочую карточку.
- Уведомления команде идут назначенному актуальному сотруднику, иначе в `MANAGER_CHAT_ID` или владельцам из `ADMIN_IDS`. Если нет получателей, намерение остаётся в `ticket_alerts`, а не теряется. В уведомлениях только номер/ссылка, без текста и адреса. Доступ по кнопке всё равно проверяется в личке.

### Повторы, черновики и хранение

Операции и ключи повторов хранятся в `service_requests`. Ключ связан с автором, типом и fingerprint тела; повтор после отзыва роли не обходит ACL. Совпавшее уже обработанное действие не добавляет второй ответ, не назначает заново и не возобновляет закрытый кейс.

Свободный текст для подтверждения хранится отдельно в `service_drafts`, только после согласия/проверки доступа. Общие состояния содержат ссылку на черновик, не копию текста/адреса. Время preview — 15 минут. Worker очищает private drafts через сутки после истечения; промежуточные версии тоже дожидаются этой очистки. Отмена блокирует старое подтверждение и не отменяет действие, уже зафиксированное транзакцией. Исполнение старого preview не стирает более новый активный черновик.

`/resume` восстанавливает ввод; на паузе новые сообщения в него не записываются. После конфликта версии нужно открыть актуальную карточку, прочитать изменения и подготовить новое подтверждение — не подменять версию в старом запросе. Обычные Telegram updates остаются best effort; дедупликация сообщений использует настоящий `message_id`.

Финансовый worker выполняет `queue_ticket_alerts` и очистку черновиков; обычный notification worker доставляет outbox с повтором. Ни в одном из них нет carrier API или автоматического возврата. Ошибка БД должна оставить либо всю операцию вместе с намерением уведомления, либо ни одного её эффекта. Сетевой сбой доставки уведомления не откатывает состоявшееся действие; возможен повтор сообщения (at least once).

История предложений, обращения, сообщения и ключи идемпотентности автоматически не удаляются. Политику ограничения/удаления, сроки, backups и право доступа необходимо утвердить отдельно. Не добавлять тело обращения, адрес или сырой Telegram update в общие логи, аудит или групповые уведомления.

### Контрольные запросы операций

Только чтение в защищённом административном окружении. Не публиковать результаты; не исправлять ими факт вручения, согласие, платёж или резерв.

```sql
-- Активные покупки, которым нужно согласование/обновление условий.
SELECT u.purchase_id, p.status AS money_status, d.state,
       q.quote_id, q.status AS quote_status, q.expires_at
FROM delivery_plans d
JOIN purchases u ON u.purchase_id=d.purchase_id
JOIN payments p ON p.payment_id=u.payment_id
LEFT JOIN delivery_quotes q ON q.quote_id=d.current_quote_id
WHERE d.state='not_sent' AND p.status IN ('pending','paid')
  AND u.fulfillment NOT IN ('completed','cancelled','expired')
  AND (q.quote_id IS NULL OR q.status<>'accepted'
       OR q.expires_at<=CAST(strftime('%s','now') AS INTEGER));

-- Действующие паузы передачи. Уже отправленные покупки сюда не попадают.
SELECT t.ticket_id, t.purchase_id, t.topic, t.status, t.assigned_to, t.updated_at
FROM support_tickets t
JOIN purchases u ON u.purchase_id=t.purchase_id
LEFT JOIN delivery_plans d ON d.purchase_id=t.purchase_id
WHERE t.blocks_dispatch=1 AND t.status<>'resolved'
  AND COALESCE(d.state,'not_sent')='not_sent'
  AND u.fulfillment NOT IN ('completed','cancelled','expired');

-- Переписка не выгружается: только состояние и ответственность.
SELECT ticket_id, purchase_id, topic, status, assigned_to, version, updated_at
FROM support_tickets WHERE status<>'resolved'
ORDER BY updated_at, ticket_id;

-- Непоставленные в outbox намерения: проверить worker и получателей.
SELECT ticket_id, operation_id, assigned_to
FROM ticket_alerts WHERE queued_at IS NULL;

-- Источник физического вручения отдельно от текущего статуса денег.
SELECT d.purchase_id, d.state, d.delivered_source, d.delivered_at,
       u.fulfillment, p.status AS money_status
FROM delivery_plans d
JOIN purchases u ON u.purchase_id=d.purchase_id
JOIN payments p ON p.payment_id=u.payment_id
WHERE d.state='delivered';

SELECT purchase_id, kind, source, actor_id, created_at
FROM delivery_events ORDER BY event_id DESC LIMIT 50;

PRAGMA integrity_check;
PRAGMA foreign_key_check;
```

### Service API и тестовые окружения

`/api/service` требует подписанную initData. GET отдаёт только собственные данные; `staff=1` не расширяет доступ. POST принимает только клиентские `consent`, `ticket_new`, `ticket_reply`, `delivery_answer`, `received` и стабильный `operation_id`. Рабочие действия, поля `internal`/`staff`/`user_id` и изменение оплаты через этот endpoint не разрешены. Для изменений существующей сущности нужен `version`; неизвестный результат/503 повторять без изменения тела и ключа. Прочтение/API возвращают `no-store`.

Mini App текущей версии использует только GET этих данных. Подтверждения/ответы — в чате. Закрытие companion-панели очищает её текст и блокирует восстановление запоздавшим ответом. Переписка не записывается в браузерное хранилище.

Тестовый `tools/ui_test_server.py` имеет явную операционную fixture с вымышленными условиями/сообщениями и публичными ID/токеном. `tools/bot_demo.py` позволяет переключать всех семерых тестовых участников (включая финансовую роль) без авторизации. **Оба инструмента — только офлайн-проверка, не production и не настоящие тарифы.** Не переносить их БД, количества или тарифы в рабочие данные. Новые runtime-модули входят в Docker, tools/tests — нет.

5. Согласовать, кто и где делает внешнюю сверку, проверяет привязку/плательщика и исполняет подтверждённый возврат. **В этом пульте нет выполнения возврата, приёма «скриншота оплаты» как денег, перепривязки поступления или снятия блокировки.**
6. Подтвердить политику доступа/хранения текста финансовых заметок и backups. При отсутствии согласованного владельца записи свободный текст не принимается; вместо него используются только структурированные этапы.

Миграция исторических исключений идёт порциями: интерфейс показывает уже материализованные рабочие задачи, а не гарантированно полный мгновенный перечень всей большой старой базы. Приём новых денежных событий и связанные изменения задач атомарны; локальный сканер — механизм восстановления. Он не сверяет кабинет или баланс провайдера.

### Рабочий процесс и закрытие

- `F…` — задача разбора, `R…` — оригинальное поступление. Неизвестная покупка не означает, что поступление можно удалить или забыть.
- «Взять» назначает себя; другой сотрудник не может перехватить занятый кейс. Для чужого снятия назначения нужен владелец. На работающий кейс влияют актуальные роль, назначение и `version`.
- Рабочие этапы `working`, `waiting`, `escalated`, отметка просмотра и заметки **не меняют** `payment_attention`, ledger, stock или delivery. Пауза отправки по деньгам проверяется прежним ядром.
- `closed` разрешён только после исчезновения исключения в **самом источнике**, с перепроверкой в транзакции. Например, `issued` + реально сохранённая подходящая invoice binding, либо `processed_at` у inbox. Одна строка `issued` без binding или очистка текста inbox-ошибки не являются завершением.
- Закрытие задачи выдачи счёта не означает оплату; закрытие такой задачи рядом со спорным поступлением не снимает блокировку той покупки. У поступлений на сверке/возврате и конфликтов нет ручной кнопки «исправить деньги».
- Новое финансовое evidence меняет fingerprint и версию. Старую форму нельзя подтвердить с новой версией автоматически. Открой актуальную карточку и осознанно подготовь новое действие.
- Вновь возникшее исключение открывает закрытую задачу без старого назначения и срока. История прежнего закрытия остаётся.

### Сроки, worker и маршрутизация

`payment_inbox_loop` примерно раз в пять секунд выполняет `sync_finance()` и `queue_finance_alerts()`. Обнаружение: `uncertain`, `legacy_unverified`, `creating` старше двух минут; проблемные/исторические receipts, конфликты, fallback по money status, необработанные inbox с ошибкой. Один проход ограничивает каждую выборку новых источников и последовательную перепроверку до 50 записей (программный максимум параметра `limit` — 200). Индексы исключений отделяют обычные оплаченные receipts от recovery-поиска; тела всех конфликтов в память не загружаются.

Явные сроки: через 1/4/24 часа; `0` во внутреннем store — отдельное подтверждённое снятие срока, не default. В срок — напоминание ответственному; через час просрочки — владельцам. До назначения срока таймера нет. Дата не обещается покупателю как дата возврата.

Адресаты финансовой очереди:

1. Для обычного события/срока — действующий назначенный `finance` или владелец.
2. Для эскалации — владельцы из `ADMIN_IDS`.
3. Если адресата нет — владельцы, затем текущие сотрудники `finance` (до 25), затем `MANAGER_CHAT_ID`.
4. Совсем нет адресатов — намерение остаётся непоставленным в outbox, чтобы можно было исправить конфигурацию и повторить worker.

За проход создаются напоминания не более чем для 50 наступивших сроков и обрабатываются до 50 ожидающих намерений. Повтор той же генерации не создаёт новые уведомления. Перенос/снятие срока, смена назначения и отзыв роли сохраняют/меняют срок по смыслу действия и увеличивают `due_generation`. Само добавление заметки не отменяет действующий таймер. Лишнее уведомление сотруднику о том, что он только что назначил себя, не создаётся.

Перед сетевой отправкой `finance_notification_current` повторно сверяет адресата, роль, срок, генерацию и состояние. Старые reminders после переноса/закрытия/отзыва роли и снятая эскалация подавляются. Такие задания получают технический `delivered_at` без вызова Telegram: этот столбец здесь означает завершение обработки задания, а не гарантированное прочтение/получение человеком. Уже доставленные сообщения удалённо не отзываются. При сетевой неопределённости возможен повтор (at least once).

Старое уведомление денежного ядра и уведомление рабочего пульта имеют разные цели: общее изменение покупки/поступления и контроль финансовой задачи. В обоих теперь только безопасные номера/ссылки и общий смысл. Ни текст заметки, ни provider ID, плательщик или сумма не копируются в групповое сообщение. Кнопка из группы не даёт права читать карточку.

### Приватные заметки, повторы и хранение

До 800 символов и 500 заметок на задачу. Черновик до подтверждения — в `service_drafts`, 15 минут; общий `states` содержит только token/флаг паузы. На паузе произвольные сообщения не записываются. `/cancel` создаёт долговечный признак отмены, поэтому старый preview не возобновляет отправку. Повтор отправленного текста с тем же ключом не добавляет заметку, с другим телом — ошибка. Роль проверяется и перед возвратом прежнего результата.

Исполнение старого черновика не удаляет более новый и приостанавливает скрытый ввод. Если версия стала старой, автор с действующим правом/согласием может прочитать и скопировать текст до истечения draft, но не отправить его без новой проверки. В `service_requests`, `staff_audit`, `finance_journal`, `chat_actions` и уведомлениях не хранится копия текста заметки; используются fingerprint и ссылки.

Очистка удаляет private drafts через сутки после истечения. Финансовые события, задачи, заметки, журналы и ключи повторов автоматически не удаляются. Защищай основную БД, WAL и резервные копии; политику законного хранения/удаления нужно утвердить отдельно. Новый финансовый staff API не добавлен: `/api/service` остаётся customer-only даже при подписи владельца магазина.

### Контрольные запросы финансового пульта

Только чтение в защищённом окружении. Не отправлять результаты в общий чат. Не менять строки этих таблиц для «исправления» платежа/возврата; закрытие рабочего кейса не является финансовым доказательством.

```sql
-- Материализованные задачи и актуальные версии, без приватных заметок.
SELECT case_id, source_kind, source_id, active, state, assigned_to,
       version, due_at, due_generation, updated_at
FROM finance_cases WHERE active=1 OR state<>'closed'
ORDER BY case_id;

-- Внутренние сроки; их отсутствие не интерпретируется как просрочка.
SELECT case_id, assigned_to, due_at, due_generation
FROM finance_cases
WHERE state<>'closed' AND due_at<=CAST(strftime('%s','now') AS INTEGER)
ORDER BY due_at, case_id;

-- Неадресованные намерения: проверить worker и действующие роли/ADMIN_IDS.
SELECT a.alert_id, a.case_id, a.kind, a.generation,
       f.state, f.assigned_to, f.due_at, f.due_generation
FROM finance_alerts a JOIN finance_cases f ON f.case_id=a.case_id
WHERE a.queued_at IS NULL ORDER BY a.alert_id;

-- Должно быть пусто при штатной работе: не «чинить» этот запрос ручным UPDATE.
SELECT case_id, source_kind, source_id, version
FROM finance_cases WHERE state='closed' AND active=1;

-- Контроль лимита заметок без выгрузки их текстов.
SELECT case_id, COUNT(*) AS notes FROM finance_notes
GROUP BY case_id HAVING COUNT(*)>=500;

-- Журнал шагов/источника: тела заметок здесь отсутствуют.
SELECT event_id, case_id, actor_id, kind, created_at
FROM finance_journal ORDER BY event_id DESC LIMIT 50;

-- Количество записей с обязательным разделением происхождения и валюты.
-- Денежные итоги смотреть в /finance: legacy и конфликтующие повторы не складываются.
SELECT source, method, currency, status, COUNT(*) AS original_records
FROM payment_receipts GROUP BY source, method, currency, status;

-- Слово issued без подходящей сохранённой привязки не разрешает закрытие.
SELECT a.attempt_id, a.payment_id, a.method
FROM payment_invoice_attempts a JOIN payments p ON p.payment_id=a.payment_id
WHERE a.status='issued' AND NOT EXISTS (
    SELECT 1 FROM payment_invoices i
    WHERE i.payment_id=a.payment_id AND i.method=a.method
      AND i.external_ref=a.external_ref AND i.currency='RUB'
      AND i.amount_minor=p.amount_rub*100
);
```

### Обновление и проверка данных

1. Сделать проверяемую резервную копию SQLite/WAL, рабочего каталога и кода. Проверить аддитивную миграцию на защищённой копии без второго production polling.

5. Проверить первое сохранение, отказ, повтор, две разные учётные записи, перезапуск и удаление выбора. Согласие на списки не разрешает контакты/рекламу; сотрудники не получают обход приватности через роль.
6. Согласовать тексты разрешения и правила доступа/хранения резервных копий. Эта реализация не является автоматическим подтверждением юридического соответствия и не заменяет общую политику обработки данных.

Новых ключей/обязательных настроек `.env` нет. Источники runtime добавлены в Docker; demo и tests в образ не включены. Root seed-каталог и production-настройки этой очередью не заменялись.

### Сроки, очистка и удаление

- Поисковая сессия действует **24 часа** после создания/изменения. По истечении старое поколение больше не принимается. Чтение само по себе срок не продлевает.
- В строке сессии — только фильтры, IDs совпавших товаров и digest каталога. В `states` поискового шага — поколение, revision и флаг паузы, не свободный текст.
- `payment_retry_loop` вызывает `prune_discovery` примерно раз в **300 секунд**: удаляются истёкшие сессии и `service_requests` видов `discovery_input`/`discovery_search` старше **семи дней**. Дубликаты успешного поискового сообщения не передаются новому мастеру ввода. Fingerprint не является шифрованием, а запрет сырых логов нужно сохранять и в будущей телеметрии.
- `discovery.*` callback tokens действуют **20 минут**. Общая очистка `prune_commerce` удаляет их спустя сутки после истечения; это не продлевает право выполнить кнопку. При отключении хранения discovery payloads удаляются сразу.
- `/saved` → «Настройки списков» → «Удалить выбор и отключить…» требует отдельного подтверждения. Одна транзакция очищает оба списка, параметры поиска, discovery-ввод и старые действия, выключает хранение и продвигает поколение согласия.
- Минимальная строка отключённого аккаунта, служебные события и ключи идемпотентности согласия/списков остаются для защиты от повторов. В `events` новых действий нет поисковой фразы и product IDs списка; события фиксируют разрешение и факт добавления/удаления по типу списка.
- Корзина, контактный профиль, покупки, финансовая история, другие черновики и backups этой кнопкой не стираются. SQLite/WAL и резервные копии требуют собственного регламента. Доступ оператора к файлу БД технически позволяет читать предпочтения — UI-изоляция не шифрует БД.
- Уже отправленные сообщения Telegram и текст временной истории demo эта DB-очистка не удаляет. Отдельный общий запрос на удаление персональных данных не следует считать исполненным только по пустому избранному.

При остановленном/ошибающемся worker физическая очистка может отставать. Время действия сессии/token всё равно проверяется при обращении. Наблюдать ошибки фонового цикла; не «лечить» их удалением money/audit таблиц. Для повторной включённой учётной записи создавать актуальные кнопки — старая форма согласия не должна восстанавливаться.

### Контрольные запросы подбора

Только чтение в защищённой копии/консоли. Не отправлять результаты с пользовательскими идентификаторами в общие чаты. SQL не заменяет пользовательское подтверждение удаления и не должен применяться для обхода согласия.

```sql
-- Разрешённое/отключённое хранение. Просмотр без согласия не создаёт аккаунт списка.
SELECT enabled, COUNT(*) AS accounts
FROM discovery_accounts GROUP BY enabled;

-- Объём списков без выгрузки конкретных предпочтений.
SELECT kind, COUNT(*) AS items, COUNT(DISTINCT user_id) AS accounts
FROM discovery_items GROUP BY kind;

-- Должно быть пусто: лимиты на пользователя проверяются атомарно.
SELECT user_id, kind, COUNT(*) AS items
FROM discovery_items GROUP BY user_id, kind
HAVING (kind='saved' AND COUNT(*)>50) OR (kind='compare' AND COUNT(*)>3);

-- Должно быть пусто: отключённое хранение не оставляет активные списки.
SELECT i.item_id, i.user_id, i.kind
FROM discovery_items i JOIN discovery_accounts a ON a.user_id=i.user_id
WHERE a.enabled<>1;

-- Истёкшие сессии: допустимо краткое отставание до следующего цикла очистки.
SELECT user_id, revision, datetime(expires_at,'unixepoch') AS expired_at_utc
FROM discovery_sessions WHERE expires_at<=CAST(strftime('%s','now') AS INTEGER)
ORDER BY expires_at LIMIT 50;

-- Минимальные маркеры повторов: без исходных запросов или action payloads.
SELECT kind, COUNT(*) AS markers, MIN(created_at) AS oldest
FROM service_requests
WHERE kind IN ('discovery_input','discovery_search','discovery_list','discovery_consent')
GROUP BY kind;

-- Долго не вычищенные discovery payloads: проверить общий prune_commerce.
SELECT COUNT(*) AS overdue_action_rows FROM chat_actions
WHERE kind LIKE 'discovery.%'
  AND expires_at<CAST(strftime('%s','now') AS INTEGER)-86400;

PRAGMA integrity_check;
PRAGMA foreign_key_check;
```

### Эксплуатационные правила

- Правила опубликованного/созданного кода через интерфейс не редактируются. Для других правил — новый код; прежнее имя не переиспользуется, лимиты повторным включением не обнуляются. Флаг «включён» не отменяет временное окно и остальные условия.
- Остановка запрещает **новые** применения. Уже созданный счёт сохраняет скидку и платёжную сумму. Не менять `payments.amount_rub`, `orders.amount_rub` или JSON snapshot для «отмены скидки».
- Скидка записывается целыми рублями, распределение связано с `order_id`; сумма net-строк должна совпадать с оплатой. Это не receipt о поступлении и не выполненный возврат. Фискальная интеграция этим модулем не производится.
- Отмена/истечение покупки освобождают склад по прежним правилам, **не квоту промокода**. Позднее поступление разбирается прежним платёжным ядром. Нельзя возвратом квоты или сменой статуса снимать финансовое исключение.
- Выбор/снятие кода изменяет revision общей корзины. Обычные правки состава сохраняют код, но старая ценовая проверка недействительна; при недействующем коде нельзя молча оформить по полной цене. Очистка всей корзины снимает код.
- Повтор переносит весь допустимый состав или ничего. Он объединяется с текущей корзиной, заново проверяет суммарный SKU-остаток, очищает персонализацию добавляемых строк и текущий промокод (предупреждение до подтверждения). Профиль и старые покупки не меняются. Это не заказ, резерв или новая оплата.
- Купонный checkout пока в чате. `/api/cart` показывает только собственный выбранный код; Mini App предупреждает и направляет в `/cart`. Неподдерживаемый/старый клиент получает отказ без потери скидки. Точный retry прежней заявки ищет сохранённый receipt до проверки нового промокода, сохраняя новую корзину.

### Пауза, повторы и хранение

Owner wizard и ввод кода действуют 30 минут; action/price tokens — 20 минут. Они привязаны к аккаунту, версии и содержимому. Выход в меню приостанавливает ввод, `/resume` возобновляет после проверок. Результат успешного message ID не попадает в более новый контактный/сервисный мастер.

В `states` остаются проверенные поля мастера, а в input-маркерах — fingerprint, не свободные сообщения. Фоновой цикл примерно раз в 300 секунд удаляет истёкшие growth-состояния и `growth_input` старше семи дней. Общая очистка `chat_actions` удаляет записи спустя сутки после истечения token. Остановка worker задерживает физическую очистку, но не продлевает право выполнить истёкшую кнопку.

Кампании, записи применения, правила/распределения скидки, аудит и ключи повторов бизнес-действий автоматически не удаляются. Это связанные с покупкой записи, не избранное. Удаление discovery-списков или локального профиля не означает удаления промокода/финансовой истории. Доступ администратора к БД технически позволяет читать записи: защищать SQLite/WAL, дампы и backups; сроки хранения/удаления согласовывать отдельно.

### Контрольные запросы промокодов

Только чтение в защищённом окружении. Код, user ID и связь с покупками не отправлять в общий чат. Строки с нарушенной суммой/привязкой требуют расследования и контролируемого исправления, не автоматического UPDATE.

```sql
-- Настройки и срок UTC. active -- флаг, не доказательство текущей применимости.
SELECT promotion_id, code, active, version,
       datetime(json_extract(rules,'$.starts_at'),'unixepoch') AS starts_utc,
       datetime(json_extract(rules,'$.ends_at'),'unixepoch') AS ends_utc
FROM promotions ORDER BY promotion_id DESC LIMIT 50;

-- Оформления, не платежи/выручка. used не должен превышать общий лимит.
SELECT p.promotion_id, p.code, COUNT(r.payment_id) AS used,
       json_extract(p.rules,'$.total_limit') AS total_limit
FROM promotions p LEFT JOIN promotion_redemptions r USING(promotion_id)
GROUP BY p.promotion_id;

-- Должно быть пусто: превышение личной квоты.
SELECT r.promotion_id, r.user_id, COUNT(*) AS used
FROM promotion_redemptions r JOIN promotions p USING(promotion_id)
GROUP BY r.promotion_id,r.user_id
HAVING COUNT(*)>json_extract(p.rules,'$.user_limit');

-- Должно быть пусто: сумма, владелец и позиции сохранённой покупки согласованы.
SELECT r.payment_id, r.user_id, r.subtotal_rub, r.discount_rub, r.total_rub,
       p.amount_rub, p.status
FROM promotion_redemptions r JOIN payments p USING(payment_id)
WHERE p.user_id<>r.user_id OR p.amount_rub<>r.total_rub
   OR r.total_rub<>r.subtotal_rub-r.discount_rub
   OR r.total_rub<>COALESCE((SELECT SUM(o.amount_rub) FROM orders o WHERE o.payment_id=r.payment_id),0);

-- Должно быть пусто: распределение скидки сохраняет все три суммы.
SELECT r.payment_id FROM promotion_redemptions r LEFT JOIN json_each(r.allocations) a
GROUP BY r.payment_id
HAVING COALESCE(SUM(json_extract(a.value,'$.subtotal_rub')),0)<>r.subtotal_rub
    OR COALESCE(SUM(json_extract(a.value,'$.discount_rub')),0)<>r.discount_rub
    OR COALESCE(SUM(json_extract(a.value,'$.amount_rub')),0)<>r.total_rub;

-- Должно быть пусто: каждое распределение связано с нужной реальной net-строкой.
SELECT r.payment_id, json_extract(a.value,'$.order_id') AS allocated_order
FROM promotion_redemptions r JOIN json_each(r.allocations) a
LEFT JOIN orders o ON o.id=json_extract(a.value,'$.order_id')
WHERE o.id IS NULL OR o.payment_id<>r.payment_id OR o.user_id<>r.user_id
   OR o.amount_rub<>json_extract(a.value,'$.amount_rub') OR o.amount_rub<=0;

-- Неприменимые сейчас выборы -- не обязательно порча данных. Клиенту нужна перепроверка/снятие.
SELECT c.user_id, p.promotion_id, p.code FROM cart_promotions c
JOIN promotions p USING(promotion_id)
WHERE c.promotion_version<>p.version OR p.active=0
   OR json_extract(p.rules,'$.starts_at')>CAST(strftime('%s','now') AS INTEGER)
   OR json_extract(p.rules,'$.ends_at')<=CAST(strftime('%s','now') AS INTEGER);

-- Истёкшие мастера: краткое отставание до следующей успешной очистки допустимо.
SELECT user_id, state FROM states WHERE state LIKE 'growth_%'
AND json_extract(data,'$.expires_at')<=CAST(strftime('%s','now') AS INTEGER);

-- Технические ключи; без выгрузки fingerprint или содержимого пользовательского ввода.
SELECT kind, COUNT(*) AS markers, MIN(created_at) AS oldest
FROM service_requests WHERE kind LIKE 'growth_%' GROUP BY kind;

PRAGMA integrity_check;
PRAGMA foreign_key_check;
```

### Включение после проверки

1. Сделать проверяемую копию SQLite/WAL, рабочего каталога и кода. Миграцию проверить на защищённой копии без второго боевого polling.
2. Добавляются `product_alert_accounts`, `product_watches`, `product_alert_deliveries`, `product_alert_stock`, индексы и идемпотентный `next_attempt_at`. Существующий лист ожидания/избранное/контактное согласие **не импортируются**, деньги/остатки не мигрируют.
3. По умолчанию `PRODUCT_ALERTS_ENABLED=0`: новые подписки и отправки выключены, просмотр/отписка доступны. Для согласованного включения установить `1` и публичную HTTPS-политику. `PRODUCT_ALERTS_POLICY_URL` имеет приоритет над `PRIVACY_URL`; без обоих или с невалидным URL подписка/доставка не разрешаются. Допустимы `1/true/yes/on`, остальные значения не включают механизм.
4. Утвердить юридические условия/регламент коммуникаций и хранения данных. Новое согласие относится к конкретному условию, не к общей рекламе. В БД фиксируются версия текста и fingerprint URL, **не архив содержимого политики**. После смены URL/версии прежние неподтверждённые сигналы требуют нового согласия.
5. Проверить точность product IDs, характеристик и SKU. Не использовать `stock_label` как остаток, не переиспользовать ID для другой вещи, не поднимать базовую цену ради видимого снижения. Подписка на цену не включает промокоды, доставку и наличие.
6. Пройти реальные Telegram-проверки на отдельном боте: создание/отказ/отписка, точный размер, цена, блокировка чата, сетевой timeout, 429, рестарт после claim, поздний ack, смена карточки/политики, большая очередь. Сам факт прохождения локальных тестов этого не заменяет.

Не изменять production `.env` или данные по инструкции демо. `example.invalid` и кнопки его лаборатории — вымышленные условия, не боевые юридические документы. Тестовые настройки включены только в `tools/bot_demo.py`; инструмент в runtime-образ не входит.

### Работа и диагностика

- Отдельный `product-alert-worker` примерно каждые 30 секунд проверяет до 200 условий и начинает до пяти отправок. Платёжный outbox/worker остаётся отдельным. При выключенном флаге или отсутствии политики новые product-сигналы не отправляются.
- Подписка — на 30 дней, до 20 активных условий пользователя, один сигнал на условие. Размер уже в наличии или ценовой порог уже достигнут при настройке — новая подписка не создаётся.
- Частота: максимум две начатые попытки за скользящие 24 часа, минимум пять минут между ними. Отписка/перезапуск не обнуляют pacing. Неизвестный исход тоже расходует попытку.
- Для размера ведётся бюджет оповещений по наблюдаемому свободному количеству. Это **не бронь**: уведомление не выделяет товар получателю. При уменьшении остатка лишние queued-сигналы снимаются; при персональном ограничении необработанный слот может перейти другому допустимому подписчику.
- Если условие изменилось до send, запись отменяется до сетевого вызова, а допустимая подписка может продолжить наблюдение. Скрытие/изменение карточки, политики/версии или отсутствие согласия прекращают прежнее условие, а не меняют его смысл.
- `sending` и claim фиксируются **до** HTTP-вызова, без удержания DB/catalog lock на время сети. Product-сигналы используют `send_message_once`, обходящий прежний URLError/429 retry loop. Это одна попытка на уровне приложения, не обещание гарантированного exactly-once в Telegram.
- Нет подтверждённого `message_id`, network/HTTP error или сбой сохранения ack → исход неизвестен. `sending` старше 120 секунд переводится в `uncertain`, а не заново отправляется. Поздний подтверждённый результат той же попытки допустим, если её не удалили/отменили.
- Не переводить `uncertain` обратно в `queued` и не вызывать `send_message` вручную для «починки»: сообщение могло прийти. Кнопки принудительной переотправки/«считать прочитанным» нет. 403 также прекращает другие живые условия недоступного чата.
- `/alertdesk` доступен только владельцу и показывает агрегаты, не предпочтения/пороги/контакты покупателей. Не пересылать SQL-выгрузки подписок в общие группы.

### Старые сценарии и удаление

`waitlist` теперь явно архив запросов интереса. Старые кнопки и `/api/waitlist` могут сохранить запрос, но требуют отдельного подтверждения через `/alerts`; клиентский флаг уведомлений его не заменяет. `/restock` и `notify_waitlist` **не рассылают** неподтверждённое наличие старой аудитории. Остаток задаётся по прежнему подтверждённому `/stock`, не по команде уведомления.

Новые сервисные запросы без старого контактного согласия исключаются из прежних broadcast-сегментов через `service_only`; общий контактный шаг не расширяет такое решение. Отправитель `/broadcast` перепроверяет этот маркер и блокировку перед очередным адресатом. Старые несервисные согласия не объявляются новыми — полный маркетинговый регламент/интерфейс остаётся отдельной задачей.

Одна подписка отключается кнопкой без второго подтверждения. `/alertsoff`/общая кнопка выключает механизм для аккаунта, продвигает поколение и удаляет записи подписок, связанные deliveries/историю, `watch.*` actions и ввод порога. Уже начатое сообщение может дойти; поздний ack не восстанавливает удалённые предпочтения.

Корзина, профиль, покупки, избранное, промокоды и старый `waitlist` не удаляются, сообщения Telegram не отзываются. Транзакционные и операционные уведомления этой командой не отключаются. Минимальная строка аккаунта, поколение, последние два timestamp и ключи повторов/события остаются; product IDs/пороги не помещаются в новые технические events.

История закрытых условий — до 30 дней после зафиксированного закрытия при работающей очистке. Проверка/prune примерно каждые 300 секунд также убирает истёкший 15-минутный ввод, input-маркеры старше семи дней и ненужные наблюдения SKU. Общий commerce-prune физически удаляет action tokens через сутки после их 20-минутного срока; общий opt-out удаляет `watch.*` payloads сразу. Остановка worker задерживает физическую очистку, а SQLite/WAL/backups требуют собственного защищённого регламента. Это не полное или физически гарантированное удаление аккаунта.

### Контрольные запросы продуктовых сигналов

Только чтение в защищённой копии/консоли. Строки с user IDs и связями наблюдений — приватные. Агрегаты являются состоянием текущих записей, а не неизменяемой аналитикой всех сообщений за историю: пользователь может удалить свои записи.

```sql
-- Параметры аккаунтов и ближайшее разрешённое время попытки; не контакты/предпочтения.
SELECT user_id,enabled,generation,json_array_length(attempt_times) AS retained_attempts,
       datetime(next_attempt_at,'unixepoch') AS next_attempt_utc
FROM product_alert_accounts ORDER BY user_id LIMIT 50;

-- Живые и завершённые условия, без выгрузки конкретных вещей.
SELECT kind,state,COUNT(*) AS watches FROM product_watches GROUP BY kind,state;

-- Техническая очередь: sent означает подтверждённый message_id, не прочтение.
SELECT state,COUNT(*) AS deliveries,datetime(MIN(created_at),'unixepoch') AS oldest_utc
FROM product_alert_deliveries GROUP BY state;

-- Должно быть пусто: по одному живому условию типа/варианта на аккаунт.
SELECT user_id,kind,product_id,size,COUNT(*) AS duplicates
FROM product_watches WHERE state IN ('watching','queued','sending')
GROUP BY user_id,kind,product_id,size HAVING COUNT(*)>1;

-- Должно быть пусто: queued/sending относится к актуальному разрешению аккаунта.
SELECT w.watch_id,w.user_id,w.state FROM product_watches w
JOIN product_alert_accounts a USING(user_id)
WHERE w.state IN ('queued','sending') AND (a.enabled=0 OR a.generation<>w.generation);

-- Должно быть пусто: ценовой порог положительный и строго ниже фиксированной базы.
SELECT watch_id,user_id FROM product_watches WHERE kind='price'
AND (anchor_rub IS NULL OR limit_rub IS NULL OR limit_rub<1 OR limit_rub>=anchor_rub OR size<>'');

-- Зависшие отправки: исход неизвестен; НЕ возвращать их вручную в очередь.
SELECT delivery_id,watch_id,datetime(started_at,'unixepoch') AS started_utc
FROM product_alert_deliveries WHERE state='sending'
AND started_at<=CAST(strftime('%s','now') AS INTEGER)-120;

-- Должно быть пусто: подтверждённое состояние имеет техническое основание.
SELECT delivery_id,watch_id FROM product_alert_deliveries
WHERE state='sent' AND (message_id IS NULL OR message_id<=0 OR started_at IS NULL OR finished_at IS NULL);

-- Должно быть пусто: бюджет сообщений ограничен последним наблюдением, не меняет stock_items.
SELECT product_id,size,last_available,credits FROM product_alert_stock
WHERE credits<0 OR (last_available IS NULL AND credits<>0)
   OR (last_available IS NOT NULL AND credits>last_available);

-- Должно быть пусто: состояния живой очереди и подписки согласованы.
SELECT d.delivery_id,d.watch_id,d.state,w.state AS watch_state
FROM product_alert_deliveries d JOIN product_watches w USING(watch_id)
WHERE (d.state='queued' AND w.state<>'queued') OR (d.state='sending' AND w.state<>'sending');

PRAGMA integrity_check;
PRAGMA foreign_key_check;
```
