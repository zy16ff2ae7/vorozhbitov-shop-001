# Аудит vorozhbitov-shop-001

Витрина запущена локально и открыта в предпросмотре: `preview_server.py`, порт **4173**.

## Итог

Проект в заметно лучшем состоянии, чем типичный «бот из одного файла». Подпись
`initData` проверяется правильно, вебхуки оплаты проверяются по HMAC, цена и товар
не берутся из браузера, статусы заказов имеют конечный автомат переходов, есть 29
проходящих тестов и smoke-тест. Ничего критичного «наружу» я не нашёл: обход путей
закрыт, SQL параметризован, `.env` не в гите, токенов в истории нет.

Основные риски — не во внешнем периметре, а внутри: **парсер цены может выставить
клиенту счёт в 10–10000 раз больше**, соединения SQLite текут под нагрузкой, а
рассылка морозит бота целиком. Ниже по приоритетам.

Проверки, которые я прогнал: `py_compile` (ок), `node --check` (ок), `unittest`
29/29 (ок), `smoke_test.py` (ок), плюс ручные пробы HTTP-эндпоинтов, нагрузка,
обход путей, разбор цен и подсчёт файловых дескрипторов.

## Критично

### 1. Парсер цены склеивает все цифры — реальный риск неверной суммы списания

`payments.py:parse_price_rub` берёт **все** цифры строки и склеивает их:

```python
digits = "".join(PRICE_RE.findall(str(value or "")))   # PRICE_RE = r"\d+"
```

Цена — свободная строка: её вводит админ в мастере `/add` (шаг `price`,
`bot.py:1206`), а `Catalog.reload` проверяет только что это `str` (`bot.py:249`).
Фактически проверено:

| Админ ввёл | Спишется |
|---|---|
| `4 900 ₽` | 4 900 ₽ ✅ |
| `4 900,50 ₽` | **490 050 ₽** |
| `1 200 - 1 500 ₽` | **12 001 500 ₽** |
| `4900 (со скидкой 3900)` | **49 003 900 ₽** |

Сумма идёт прямо в `line_amount` → `accept_checkout` → счёт Лавы/крипты/звёзд.
Опечатка с копейками или диапазоном — и клиент получает счёт на сотни тысяч рублей.
Тест `test_price_and_stars_math` проверяет только чистый формат `"11 900 ₽"`.

**Что сделать:** хранить цену числом (`price_rub: int`) и форматировать для показа;
как минимум — валидировать ввод в мастере и в `Catalog.reload` строгой регулярностью
(одно число + необязательный `₽`), отклоняя всё остальное.

### 2. Утечка соединений SQLite под нагрузкой

`Database.connection()` кэширует соединение в `threading.local()`, а
`ThreadingHTTPServer` создаёт **новый поток на каждый запрос**. Соединение
закрывается только когда сборщик мусора доберётся до словаря локальных данных
мёртвого потока. Замер:

```
baseline fds: 10
после 300 коротких потоков: 254 открытых fd
после gc.collect():         147
```

То есть каждый HTTP-запрос открывает новое соединение + прогоняет `PRAGMA
journal_mode=WAL`, `foreign_keys`, `busy_timeout`. При устойчивом трафике это
упирается в `ulimit -n` и роняет и витрину, и бота (у них одна база).

**Что сделать:** пул соединений или одно соединение под мьютексом; либо явно
закрывать соединение в `finally` обработчика запроса.

## Важно

### 3. Рассылка полностью замораживает бота

`confirm_broadcast` (`bot.py:2323`) шлёт сообщения синхронно с `time.sleep(0.04)`
внутри единственного потока опроса (`polling_loop` → `handle_update` → рассылка).
10 000 подписчиков = **~6.7 минуты**, когда бот не отвечает никому: ни заказы, ни
`/start`, ни оплата. Плюс `getUpdates` не вычитывается и апдейты копятся.

**Что сделать:** выполнять рассылку в отдельном потоке с очередью и сохранять
прогресс, чтобы её можно было продолжить после перезапуска.

### 4. Нет ограничения частоты запросов на пишущих эндпоинтах

`/api/checkout`, `/api/pay`, `/api/my-orders/cancel` не имеют троттлинга. 60
параллельных POST на отмену прошли без сопротивления. Подписанный `initData`
действителен **48 часов** (`WEBAPP_INIT_MAX_AGE`, проверено: 47 ч принимается), так
что один перехваченный `initData` даёт двое суток на автоматизированные попытки —
создание заявок, спам менеджеру в Telegram, нагрузка на базу.

**Что сделать:** лимит по `user_id` и по IP на пишущие пути; срок жизни `initData`
сократить до 1–24 ч.

### 5. Каталог меняется без блокировки, пока его читают HTTP-потоки

Локов в `bot.py` нет вообще. `/reload` и мастер `/add` вызывают
`catalog.reload()` / `catalog.save()` (`bot.py:2171, 2226-2227`), полностью подменяя
`self.data` и `self.products_by_id`, в то время как потоки `/api/catalog` и
`_checkout` читают те же объекты. Окно узкое, но исход — отдача полупустого каталога
или заявка на исчезнувший товар.

**Что сделать:** `threading.RLock` вокруг чтения/подмены каталога либо атомарная
замена собранного объекта одним присваиванием.

### 6. Боевые Telegram ID зашиты в код как значения по умолчанию

```python
os.getenv("ADMIN_IDS", "6040375660,900161382")   # bot.py:185
os.getenv("MANAGER_CHAT_ID", "5527514919")       # bot.py:188
```

Если `.env` не подхватился, бот молча выдаёт админские права этим аккаунтам, а
заявки клиентов с телефонами и адресами уходят в чат `5527514919`. Для чужого
развёртывания это утечка персональных данных.

**Что сделать:** пустые значения по умолчанию; при отсутствии `ADMIN_IDS` —
предупреждение в лог.

## Стоит поправить

### 7. Секции оплаты нет в `.env.example`

В коде читаются, в примере отсутствуют: `LAVA_SHOP_ID`, `LAVA_SECRET_KEY`,
`LAVA_HOOK_KEY`, `LAVA_ADDITIONAL_KEY`, `CRYPTO_PAY_TOKEN`, `STARS_ENABLED`,
`STARS_RUB_PER_STAR`. В README они описаны — то есть расходятся два источника
правды.

### 8. Нет заголовков безопасности

Отдаётся только `X-Content-Type-Options: nosniff`. Нет `Content-Security-Policy`,
`Referrer-Policy`, `Permissions-Policy`. В `app.js` двадцать мест с `innerHTML` —
да, все значения пропущены через `escapeHTML`, но CSP нужен как второй рубеж, если
одно место однажды забудут.

### 9. Мёртвый файл отдаётся наружу

`miniapp/bout-variants.html` (12 КБ, «Груша — ещё варианты») ниоткуда не
подключён, но доступен по HTTP 200. Черновик дизайна на проде. Также не
используются `assets/bot-avatar.jpg` и `assets/bot-mark.jpg` — они для BotFather,
это нормально, но стоит вынести из каталога, раздаваемого статикой.

### 10. Обработчик ссылается на несуществующий элемент

`app.js:1157` вешает обработчик на `#bottomProfile`, которого в `index.html` нет
(в нижней навигации пять кнопок, профиля среди них нет). Проверка `if ($(...))`
спасает от ошибки, но в профиль из нижней навигации попасть нельзя — либо остаток
рефакторинга, либо потерянная кнопка.

### 11. Шрифты весят 1 МБ в TTF

Пять `.ttf` на 1007 КБ против 146 КБ всего HTML+CSS+JS. Конвертация в `woff2`
обычно даёт минус 60–70% — для Mini App на мобильном интернете это самый дешёвый
выигрыш. `font-display: swap` уже стоит, это хорошо.

### 12. Мелочи

- `_head_only` выставляется в `do_HEAD` и никогда не сбрасывается (`bot.py:2820, 3116`). Сейчас безопасно только потому, что сервер работает по HTTP/1.0 без keep-alive; при включении `protocol_version = "HTTP/1.1"` ответы на HEAD начнут обрезать тело у последующих запросов.
- `stars_amount(0, ...)` возвращает `1` звезду — для нулевой суммы счёт вообще не должен выставляться (сейчас прикрыто проверкой `if amount_rub <= 0` выше по стеку).
- В тестах не покрыты `create_crypto_invoice`, `format_rub`, `lava_signature`; сам `StorefrontHandler` тестируется лишь косвенно (3 упоминания).
- В логе `unittest` видно `AttributeError: 'FakeAPI' object has no attribute 'base_url'` — тест проходит, потому что исключение проглатывается `except Exception`, но это маскирует реальный сбой выставления счёта в звёздах.

## Что проверено и сделано хорошо

- **Проверка `initData`** — правильный `WebAppData`-HMAC, `compare_digest`, контроль длины и `auth_date`, отпор на будущие даты.
- **Обход путей закрыт** — `/../bot.py`, `..%2f`, `/miniapp/../../bot.py` дают 404 (`resolve()` + `relative_to`).
- **Вебхуки оплаты** проверяются по HMAC, при неверной подписи 403; `mark_payment_paid` идемпотентен и работает в `BEGIN IMMEDIATE`.
- **Браузеру не доверяют** — цена, название и активность товара берутся из каталога на сервере, из запроса используются только `product_id`, размер и количество (лимиты 20/20).
- **Заказы** — `request_id UNIQUE` защищает от дублей, переходы статусов заданы явной таблицей, чужой заказ не отменить (проверка `user_id`).
- **SQLite** — WAL, `busy_timeout`, миграции через `PRAGMA table_info`, экранирование формул в CSV-экспорте (есть тест).
- **Согласие на обработку данных** запрашивается до сохранения телефона, есть тест `test_phone_is_not_saved_without_consent`.
- **Гигиена репозитория** — `data/` в `.gitignore` и не появляется в `git status` после запуска, токенов в истории нет, размер пака 4.1 МБ.
- **Каталог** — валидация callback-safe идентификаторов и размеров, все 9 товаров и 6 кадров lookbook ссылаются на существующие файлы, битых ссылок нет.
