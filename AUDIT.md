# Аудит проекта «ВОРОЖБИТОВ» · 2026-09-12

Срез по ветке `arena/01a09443-vorozhbitov-shop-001` (коммит `239ea4e`),
без обращения к продакшену: только код, тесты, история git и CI.

## 1. Что это сейчас

Telegram-магазин с нативным меню (без Mini App в пользовательском контуре):
витрина, корзина и оплаты (карта/СБП через Lava, крипта, звёзды), лист
ожидания, рефералы и розыгрыши, рассылки по сегментам, админ-контур
владелец/команда (пульт, покупки, клиенты, возвраты, витрина, правка вещей,
дайджесты, доступы) и веб-витрина-legacy с подписанными данными Mini App.

Цифры среза:

| Артефакт | Размер |
|---|---|
| `bot.py` | 6 720 строк, 318 def/class, 55 веток callback, 29 команд |
| `payments.py` | 202 строки (провайдеры оплат) |
| Тесты | `test_bot.py` 2 940 строк (105 тестов), `test_regressions.py` 963 (66), `smoke_test.py` |
| Зависимости | только стандартная библиотека Python (импорты: json, sqlite3, hmac, urllib, threading и т.д.) |
| CI | `.github/workflows/tests.yml`: py3.11, три сьюта, запуск по путям (bot/tests/catalog) |
| Хранилище | sqlite WAL (`data/bot.sqlite3`), `catalog.json` (файл), kv-таблица для настроек и пометок |
| Env | 21 переменная: токен, ADMIN_IDS, платёжные ключи, пути и пр. |

## 2. Сильные стороны

1. **Ноль внешних зависимостей** — нечему устаревать и ломать supply chain;
   деплой — один файл плюс stdlib.
2. **Оборонительный polling**: ядовитое обновление не клинит очередь (offset
   двигается всегда), экспоненциальный retry;
   рассылка в отдельном потоке с остановкой по STOP_EVENT и отчётом.
3. **Платежи идемпотентны**: webhook-и провайдеров переносят оплату
   pending→paid повторно без двойных начислений; статусы покупки и оплаты
   разведены («подтверждена» возможна до оплаты — деньги смотрим в payments).
4. **Дисциплина вывода**: пользовательский текст проходит `esc()` во всех
   найденных путях, включая рассылку (`_run_broadcast` экранирует); callback
   data проверяется на длину и двоеточия ещё на уровне каталога.
5. **Шум-дисциплина закреплена тестами**: описания команд ≤30 знаков, пульт
   ≤5 рядов — фичи подгоняются под предел, а не тесты под фичи.
6. **Журнал событий** (`events`) даёт аудиторию действий владельца и основу
   для экранов («что сегодня», журнал рассылок, история розыгрышей).
7. **Тестовый контур из трёх суитов** покрывает чекаут, оплаты, лимитер,
   гонки листа ожидания, polling, доступы владельца и все новые экраны;
   регрессии фаз 8–13 исполняются (блок `unittest.main()` уехал в конец файла).

## 3. Риски и долг (по приоритету)

### P1 — вес репозитория
`.git` = 422 МБ (pack 121 МБ). Топ больших blob в истории:
`video/all.html` 40 МБ (страница с base64-фильмами внутри), шесть ревизий
`video/vorozhbitov-roles.mp4` по 26–30 МБ, `surgery/screen-record-*.mov`
27 МБ. Каждый клон и каждый CI-чек тянет это целиком.
**Рецепт:** `all.html` и mp4 вынести из git (артефакты генерируются; отдать
в GitHub Releases/LFS или внешнее хранилище), `surgery/` убрать из истории
(`git filter-repo` —Rewrite согласовать с командой, ветка одна — момент
подходящий). Ожидаемый pack после чистки — единицы МБ.

### P1 — монолит `bot.py`
6 720 строк: один `route_callback` на 55 веток, экраны покупателя, команды
владельца, платёжные webhook и HTTP-витрина в одном файле. Правки фаз
8–13 уже упираются в пересечения якорей и совпадающие куски кода.
**Рецепт:** постепенный вынос без смены поведения: `admin_screens.py`,
`buyer_flow.py`, `storefront_http.py` с тем же классом-оркестратором;
начать с самых стабильных экранов (деньги/дайджест/возвраты).

### P2 — `catalog.json` как товароведческая база
Каждая правка (витрина, цена, размеры) переписывает файл целиком; блокировка
внутрипроцессная — второй процесс или ручной `vim` рядом с ботом могут
оставить половину файла. Историй версий нет, откат — только git.
**Рецепт:** либо ежедневная снапшот-копия файла в `data/backups/` (дешёво),
либо перенос продуктов в sqlite-таблицу с тем же валидатором (дороже, зато
транзакции и история правок).

### P2 — kv как склад настроек и пометок
В kv живут: порог розыгрыша, набор FAQ, текст последней
рассылки, причины возвратов, отметки напоминаний (`nudge_at:*`, `rreason:*`).
Рост неограничен: каждая оплата оставляет пометки навсегда.
**Рецепт:** договориться о префиксах и добавить ночную чистку пометок старше
N дней (кроме осознанных настроек владельца); настройки владельца со
временем вынести в таблицу `settings(key, value)`.

### P2 — тесты собирают `Settings` руками
Добавление поля `digest_hour` уронило 55 тестов одним ударом: конструктор
`Settings(...)` дублируется в нескольких местах тестов.
**Рецепт:** фабрика `make_settings(**overrides)` в общем helper тестов;
новые поля тогда не ломают ничего.

### P3 — мёртвые итерации инструментов
`tools/video/` — 17 файлов, из них ~10 исторические дубли
(`make_campaign_*` v2–v6, `make_video_*` v2–v4): суммарно тысячи строк,
которые никто не запускает. Живые — `make_role_walkthrough.py` +
`chat_render.py`.
**Рецепт:** архивная папка или удаление из ветки (история их всё равно
хранит).

### P3 — legacy Mini App живёт рядом
`handle_web_app_data`, HTTP-эндпоинты `/api/*` и подписи HMAC остаются в
коде, хотя пользовательский контур — нативное меню. Часть покрыта тестами,
часть — нет.
**Рецепт:** зафиксировать статус в README («legacy, поддерживается
подписанный контракт»), добавить смоук на `/api/my-orders` или вынести в
модуль с явной пометкой.

### P4 — наружу смотрит HTTP-сервер
`ThreadingHTTPServer` на `0.0.0.0` (нужно для preview): POST `/api/checkout`,
`/api/pay`, webhook-и провайдеров, `/api/my-orders/cancel`. Безопасность
держится на подписях (HMAC webapp, hook-ключи Lava/crypto) и
`TRUSTED_PROXY_IPS`; отдельной аутентификации у витрины нет.
**Рецепт:** держать контракт подписей под тестами (есть частично), RateLimiter
на все POST-ы (есть на части), документировать, какие пути обязаны идти
только через прокси.

## 4. Безопасность — срез

- Токены и ключи только из env; в коде и логах не печатаются.
- Гейт владельца (`is_owner` = ADMIN_IDS) отделён от команды (`is_admin`):
  grant/revoke/тумблер дайджеста/порог розыгрыша недоступны назначенным
  админам — проверено тестами.
- HTML-экранирование пользовательских строк в найденных путях вывода
  (карточки, рассылка, экраны) присутствует; сырые f-строки с чужим текстом
  в обход `esc()` не найдены при точечной проверке новых экранов фаз 8–13.
- Callback data ограничена по длине на валидации каталога; «отмена» словами
  работает во всех текстовых шагах.
- Остаточный риск: ручное редактирование `catalog.json` минуя валидатор
  может пронести битую цену (бот переживёт: parse_price_rub→0, лог есть).

## 5. Покрытие тестами

Есть: чекаут и оплаты (включая webhook-и), лимитер, гонки листа ожидания,
poison-update polling, доступы владельца, все экраны фаз 5–13 (деньги,
дайджест, витрина, клиент, возвраты, unpaid, FAQ, анонс, правка вещи,
шум-дисциплина.
Нет или слабо: тайминги потока рассылки (только факт отчёта), HTTP-витрина
вне нескольких тестов, инструменты видео (не предназначены), восстановлении
после обрыва файла каталога (только отказ с объяснением).

## 6. Дорожная карта предложений

1. Чистка веса репозитория (P1) — наибольший выигрыш при малом риске.
2. Фабрика Settings в тестах (P2) — час работы, снимает класс поломок.
3. Снапшоты `catalog.json` (P2) — страховка данных владельца.
4. Распил `bot.py` по контурам (P1) — по экрану за коммит, без смены
   поведения, тесты те же.
5. Чистка kv и архив tools/video (P2/P3) — гигиена.

Аудит не нашёл блокеров для продажи и ведения магазина текущим кодом:
найденное — это вес истории, размер файла и долгосрочная гигиена, а не
дыры в деньгах или доступе.
